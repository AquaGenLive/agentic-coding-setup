# Codex Specification Implementation

Complete all remaining authorized milestones in one continuous run, one milestone and behavior at a time. Deliver behavior, evidence, and independent acceptance; respect explicit user boundaries and the pause rules.

## 1. Roles and authority

The main conversation agent is the single Lead. It owns scope, decomposition, coordination, user communication, progress checks and acceptance; do not spawn a separate Lead or supervisor.

| Role | Owns | Model / configuration |
|---|---|---|
| Lead (main agent) | Scope, slicing, dependencies, progress, blockers, user decisions, acceptance, stop boundary | Existing main conversation; not spawned |
| Implementer (default) | Plan, tests, code, affected docs, verification | `sol_worker`, fixed `gpt-6.1-sol` / `medium` |
| Mechanical implementer | Bounded mechanical edits with straightforward acceptance criteria | `luna_worker`, fixed `gpt-6-luna` / `max` |
| Escalated implementer | Remaining work after Luna (§5), or when its task needs broader implementation judgment | `sol_worker`, fixed `gpt-6.1-sol` / `medium` |
| Independent reviewer | High-risk mechanism/proof and substantive candidate review | `default`, `gpt-6.1-sol`, `medium` |
| Expert reviewer | Bounded diagnosis and necessary-change repair plan after two unsuccessful Sol candidates (§5) | `default`, `gpt-6-astra`, `high` |
| Final escalated implementer | Remaining behavior after Sol's Astra-guided repair fails (§5) | `default`, `gpt-6-astra`, `high` |

- Default to `sol_worker` for implementation requiring judgment. Apply §3's worker-selection check before each new implementer dispatch; select `luna_worker` for eligible mechanical work and record the reason in the existing brief/status.
- Sol-first behaviors enter the Sol stage directly, without a preliminary Luna budget. If a Luna task needs broader design judgment, integration, or difficult debugging, transfer exclusive ownership to `sol_worker` at a safe handoff without exhausting the Luna budget; preserve source, evidence, findings and all unsuccessful counts.
- Subagents use `fork_turns: "none"`; default agents use the table's model/effort. If required roles/capabilities are unavailable, report and obtain a fallback choice before substitution.
- Lead spawns at most one active implementer and one independent reviewer; slices run sequentially. No further delegation by workers/reviewer, nested leads, extra supervisor, or extra worktrees/databases merely to fill slots.
- Lead may inspect source/evidence, resolve routine decisions and edit prose/tracking; **no application/test/migration/build/runtime/script edits**, including small fixes or code conflict resolution. Explicit skill editing is exempt. Reviewer is read-only, never accepts its own implementation, and substantive blockers cannot be waived by Lead.
- Replacement author takes exclusive ownership after the former author stops editing; never overlap Luna/Sol/Astra writers. Expert diagnosis uses the independent reviewer slot, not another supervisor. Same-reviewer rules below permit only the explicit §5 expert handoff; nobody reviews their own implementation.
- Work through all remaining milestones in the approved scope during one run, sequentially in the plan's dependency order. A request to implement the approved plan authorizes continuation between its milestones; an explicit milestone/range/stop limit takes precedence. Keep the same main Lead throughout the run, including compaction. Lead handles in-scope blockers and progress checks (§7), without duplicate routine reviews or command polling. Ask the user only for unresolved material requirement/scope/authority conflicts or actual capability blockers. No commit, publish, deploy, usage reset, or paid-setting change beyond existing authority.

## 2. Resume and tracking

Resolve the spec directory and read applicable repo instructions. Lead reads governing scope/acceptance/stop requirements and the relevant spec, source and build/test details. Ask only for unresolved target/material requirements. Preserve exact step names, dependencies, existing edits, accepted decisions and valid verification.

| File | Exclusive owner | Contents |
|---|---|---|
| `progress.md` | Lead | Accepted milestones, durable decisions, historical evidence links and pause/completion handoffs. No worker diary or duplicate live state. |
| `status.md` | Lead | Authorized run scope and milestone sequence (accepted/current/pending), current objective and slice sequence/brief, decisions, agent IDs/ownership, behavior records/findings (§5), blockers, execution agreement, next action/evidence and run progress-check record (§7). Replace stale state; aim ~60 lines, necessary facts take priority. |

Create missing tracking files for implementation, not skill discussion/editing. Keep live state in status and accepted outcomes in progress; link evidence rather than copying histories. Checkpoint meaningful changes and before planned pause/handoff. No simultaneous writers.

On resume/compaction, read status and relevant progress decisions; reconcile with newer user instructions and verify relevant current source/evidence. Continue the unfinished milestone, or select the next pending authorized milestone if the previous one is accepted. Preserve valid accepted work, unresolved behavior counts/escalation stages, cleanup obligations and run deadlines. Tracking never overrides requirements. Retrieve history only for a concrete gap; do not reload everything or rerun valid gates. Reopen settled decisions only for new instructions or evidence of invalidity; record why. When resuming older single-milestone tracking, derive remaining scope from the current user authorization and approved plan; a previously explicit single-milestone limit still applies. Resuming a supervised pause requires explicit user direction (§7).

When resuming the former two-coordinator workflow, obtain a finite handoff from any active delegated coordinator and end its coordination role before taking ownership. Preserve child IDs, findings, attempts, execution/cleanup obligations and check deadlines; reuse existing children when supported. Do not duplicate writers or interrupt active commands blindly. If child control cannot transfer safely, report the capability blocker rather than keeping two permanent coordinators or spawning replacements over active work. Move the current check record to status once; preserve historical progress entries.

## 3. Dispatch and slicing

Lead identifies the authorized run scope: all remaining milestones when asked to implement the approved specification/plan, or the narrower milestone/range explicitly requested. Record the exact milestone sequence, dependencies, scope/exclusions and acceptance/stop conditions in status. Merely referencing a broader specification does not expand a narrow assignment. Lead owns decomposition and dispatches workers directly; no extra managerial approval stage.

**Milestone loop:** Select the first unfinished authorized milestone in the approved dependency order. Complete its behavior slices, independent acceptance, required integration gates and cleanup before advancing (§8). At acceptance, checkpoint the outcome, report a concise progress update and automatically select the next pending milestone whose dependencies are satisfied; no new user confirmation or main conversation is required. If a dependency is missing outside the authorized scope, resolve the material scope decision before dependent work; do not skip the blocked milestone or mark it complete. Milestone acceptance is a continuation boundary; run completion, explicit user stops and the existing pause/blocker rules are stopping boundaries.

**Size implementation work before dispatch:** Lead inspects actual source/dependencies and assigns one independently verifiable behavior at a time, not an entire numbered milestone by default. Give that acceptance target a stable behavior ID (§5); slice/worker names do not define its retry budget. Each brief names the outcome, governing contracts/existing patterns, owned scope/exclusions, decisive acceptance scenarios, focused checks, and consuming integration/remaining work. In the existing brief/status, record the sizing decision in one sentence: fits as one behavior, split into dependent slices, or inseparable coupled mechanism with reason.

Split when independent mechanisms need separate design decisions (e.g. codec, quota lifecycle, expiry, publication races), or unrelated scenario families prevent one clear acceptance boundary. Keep a transaction and its atomic effects, rollback, authorization, and necessary shared-contract changes together; do not separate quota reservation from the session mutation it protects. Size by behavior and dependencies, not files, layers, time caps, or a rigid test count. Avoid tiny slices that duplicate setup/review without isolating a behavior. A small slice can still be high-risk and must follow §4; sizing does not change the model/escalation rules (§1/§5). No scaffolding-only slices, speculative interfaces, scope expansion, or skipped gates.

**Worker selection — required before each new implementer dispatch:** Assess the whole assignment, including verification and consumer integration. Select `luna_worker` when the acceptance criteria and implementation approach are fixed, existing patterns cover the changes, and no unresolved design, API, behavior or difficult debugging decisions remain. Typical eligible work includes specified presentation wrappers, copy/localization updates and repetitive wiring to established contracts. Routine consumer integration or required tests/browser proof alone do not disqualify Luna.

Select `sol_worker` when the assignment needs new mechanism/API design, financial or async/focus lifecycle decisions, nontrivial integration judgment, or diagnosis of an uncertain cause. Small size or first-pass success does not establish mechanical scope. Record one sentence in the existing brief/status: `worker + model/effort | why Luna is eligible, or which concrete requirement needs Sol`; the Sol default alone is not a selection reason. Apply this check to separately assigned verification too. Corrections retain the current author/escalation stage under §5. Preserve coupled behaviors; do not split work merely to use Luna or impose a worker quota.

Keep the same main Lead for the run, one active implementer, and the same independent reviewer subject to §5's expert handoff rules; milestones and slices run sequentially. Preserve established contracts, source/evidence and unresolved attempt counts (§5) when splitting, advancing milestones or resuming. Choose worker context using the boundary rule below, including at milestone transitions. No extra planner, managerial approval stage, or per-slice document.

**Worker context at slice boundaries:** A new independently scoped behavior gets a fresh worker with `fork_turns: "none"`; do not wait for compaction or carry a completed behavior's conversation into new work. Corrections, proof revisions and verification of the same behavior reuse its current author while available. A separately assigned integrated verification task also gets a fresh worker; a discovered defect routes to the appropriate behavior author under §5. Returning/interrupting does not clear context: implement a fresh context through replacement, never claim an in-place reset. No refresh during active execution/review and no reset of unresolved attempts or escalation stage; an escalated behavior never returns to Luna (§5).

Before replacement, obtain the former worker's final checkpoint and confirm its turn ended with no active command/restoration obligation. Retain the same reviewer. Supply only relevant source/contracts, accepted evidence, unresolved findings/counts, execution agreement and remaining integration; no inherited transcript, repeated valid gates or extra handoff document. Record exclusive ownership in status. Check capacity only at this boundary: preserve room for the independent reviewer and the applicable Sol/Astra transfer. Returned agents may still occupy capacity; expert transfer must also fit before dispatch. Retire a stopped worker only using an actually exposed supported tool; idle/interrupted does not imply a freed slot. If capacity cannot support replacement, checkpoint and report the limitation for a user fallback decision before starting the new behavior; do not silently reuse old context, exceed limits or replace the reviewer to free a slot.

**Implementer lifecycle — include in every worker brief:** At an agreed proof/candidate/verification handoff, finish owned commands and cleanup, return `outcome | source/evidence | open findings/effort | cleanup/remaining obligations | next action/owner`, then end the turn. Do not send “ready” and wait for review, acknowledgment or another assignment. This is a finite handoff, not acceptance or permission to expand scope. Mid-assignment blocking decisions still follow §3's ownership rule; do not return after every command or abandon handles. Lead uses `send_message` for active-work steering and `followup_task` on the SAME returned worker for corrections/continuation of that behavior. New independent work follows the fresh-context rule above. Never reactivate solely to acknowledge a final result. Missing reactivation/lifecycle capabilities follow §1; do not invent close/reset tools.

**Focused handoffs (all roles):** Supply assigned outcome/requirement IDs with exact spec sections; owned components/files and shared resources; dependencies/exclusions; inputs/outputs/errors/effects and shared contracts; relevant evidence, missing scenarios, unresolved findings/repair guidance, next artifact, verification, and remaining integration. Link source documents with section/function/test locations; quote only essential constraints. Do not paste entire specs, project handbooks, conversations, or completed finding histories. Recipients read applicable instructions and referenced requirements; retrieve more source/context for concrete dependencies or uncertainties. Preserve required workflow rules below, acceptance criteria, attempt counts, and ownership/restoration obligations. No arbitrary context cap or separate handoff document. Corrections to the same agent carry changed scope/source, unresolved findings, new evidence, and plan delta; fresh replacements receive the complete relevant assignment state.

**Workflow map:** Read as text; no rendering step needed. Roles/models/effort: §1. This overview does not replace detailed rules; §4 governs proof, §5 candidate counting, §6 verification, and §7 progress checks/pause at every stage.

When Luna is selected, its candidate budget is: initial submission + up to four corrections (five attempts total); explicit inability also follows §5. Early-proof feedback is separate from Luna candidate counting. Sol-first work starts at the Sol stage; Sol/Astra stages and proof-level candidate accounting follow §5. Lead verifies that slices compose into the milestone; slice review is not final acceptance. For a single slice, the boundaries coincide. Preserve any repo/plan-required earlier gates.

Outside proof/candidate checkpoints, workers act autonomously; no permission per edit/test/RED/run. Serialize conflicting fixtures, build outputs, databases, ports, and servers without repeated test-slot transfers.

Every brief states role, ownership, governing paths, shared workspace/preserve-others rule, and applicable workflow. Lead reads this skill. Workers receive plan/proof, repair-guidance use, review-before-broad-gates, attempt, pause, communication route below, and §6 execution agreement/ownership/stall rules (batched notice, autonomous repairs/runs/handle resumes, five-minute check, one recovery) explicitly. Worker briefs include §4's local-stall diagnostic and §6's end-of-behavior effort summary; documentation/release-verification briefs also include §4's evidence-first check. Reviewer briefs include §5's repair guidance and finite-request/return lifecycle. All briefs include §6's minimum-evidence/gate-ownership rule and concise-output practice: retain verbose logs, return result/evidence links and relevant failure excerpts, retrieve further output for a concrete gap. **Every worker/reviewer/escalation brief includes §6's waiting rule verbatim; Lead obeys it too**. Paths alone do not transmit rules to fresh contexts.

**Actionable notifications:**

| Route | Notify for |
|---|---|
| Worker → Lead | Required plan/delta, review-ready proof/candidate, blocker/decision, slice execution agreement or material change, execution blocker (§6), completed verification |
| Lead → user | Meaningful progress, accepted milestone, stopping boundary, pause or decision/capability blocker needing user action |
| Lead → reviewer | Ready review material (§5); material corrections during active review |

Batch related findings/evidence into one handoff: change/outcome, blocker/decision if any, next action, evidence link. Do not delay urgent correctness/safety blockers, required pre-code plans, initial/materially changed execution notices, or pause/ownership acknowledgments. No acknowledgment-only chatter, duplicate notifications, routine “starting/still running” messages, or repeated reports of unchanged state. Include these notification rules in recipient briefs. Keep routine plans, proof exchanges, findings, retries, test results and execution tracking within Lead/worker/reviewer and `status.md`. Lead communicates useful outcomes to the user without relaying internal chatter or requesting duplicate reports. Required user updates use known state, not extra team inspections.

**Next-action ownership:** Include in every worker/reviewer brief. Ordinary in-scope plans, correction deltas and progress reports are informational: publish and continue; no acknowledgment required. Required proof/candidate review, scope decisions, approvals and explicit freezes still block dependent work. A blocking handoff states `state: awaiting decision / ready for review | next owner: Lead (route to reviewer when needed) | needed decision/artifact + evidence`. Lead resolves or routes it before waiting, and returns the decision/accepted review outcome to the worker with the next action. Record only current state, next owner/action and unresolved request in status; replace superseded state.

Before waiting, Lead checks known pending handoffs, not fresh status queries: another agent must own a concrete executable next action. Generic “running” status or a published plan is insufficient. If ownership is ambiguous, clarify once. Worker awaiting a blocking request with no decision or routed-review response after its first 120-second timeout sends one clarification that it is paused awaiting the named decision; this is the sole timeout-reminder exception to §6. No reminder for an already-routed review, repeated reminders, extra monitor or approval inferred from silence. Lead treats that clarification as actionable and resolves/routes it before waiting again. Missing native messaging uses the existing finite-handoff fallback.

**Communication route:** At first dispatch, establish the recipient's actually exposed native messaging capability once, using tool definitions and the first necessary plan/notice; no extra handshake. Separately exposed collaboration APIs need not appear in a nested tool registry; registry absence alone does not prove unavailability. Use returned agent IDs. Lead records the working route or finite-handoff fallback alongside ownership in status and includes it in follow-ups. Recheck only after an actual capability failure or changed runtime, not each turn/compaction. Do not repeatedly search for tools, read parent task history, or use separate user-owned task messaging to communicate. Missing messaging uses §6's fallback; missing required delegation/reactivation follows §1. Workers/reviewer may discuss agreed contracts directly where supported; Lead resolves decisions. Use the worker-context boundary rule above; corrections preserve the current author and counts.

## 4. Plan, prove, implement

**Before editing:** The implementer inspects relevant source/tests/requirements and publishes a concrete plan to Lead for every assignment/correction. Read-only investigation/baselines may precede it; private reasoning is insufficient. Include approach, affected files/functions, reuse, change order, tests, uncertainties. Small changes need only a few bullets. This rule applies to Luna, Sol and Astra implementers. Store plan summary/link in status. For corrections, worker checks §5's repair guidance against source and publishes only the plan delta: adopted approach, evidence-backed deviations/uncertainties, changed scope/order/tests, and why the failed approach changes. Do not independently recreate the reviewer's diagnosis or full plan; investigate concrete gaps. Worker retains local implementation judgment. Reuse valid plans; no duplicated specs or per-fix plan files. Lead checks scope/dependencies/feasibility and the §3 sizing decision against every worker plan without duplicating technical review. If inspection reveals extra mechanisms, unsettled shared contracts, or substantial new dependencies beyond the brief, worker reports the sizing mismatch before expanding code; Lead narrows/splits the remaining work or explains why it is inseparable, updating the existing brief/status. Preserve valid work/evidence/counts. Pause only work dependent on that scope decision; ordinary in-scope work needs no acknowledgment. Include this expansion boundary in worker briefs.

**Documentation/release-verification assignments — evidence first:** Before finalizing the documentation candidate, include a compact map in the existing plan or acceptance matrix: `required scenario/gate → applicable source/test/result → covered / missing / uncertain / explicitly accepted limitation`. Check actual assertions and result applicability, not test names or aggregate counts; inspect further only for a concrete gap. Identify missing behavioral proof, stale evidence and incomplete required command coverage before polishing release claims. Lead resolves each gap's scope and next owner through existing sizing/verification rules; use the same reviewer when coverage is uncertain or the existing high-risk checkpoint applies. No extra agent, standalone audit document or mandatory additional review round. Unaffected drafting may continue; do not submit a completed documentation candidate while required evidence gaps have no resolved disposition. Close in-scope gaps through the normal implementation/review flow, then finalize claims against the results. Preserve valid evidence, user-accepted limitations and authorization boundaries; this audit alone neither reopens accepted scope nor authorizes additional implementation, broad reruns or deployment.

**Shared-contract test selection:** When changing a shared contract, include a short map in the existing worker plan: changed field/version/enum/key set or behavior → affected producers/consumers → existing compatibility/contract tests. Cover relevant API/UI, persistence, readiness/job inventories, localization/docs, and E2E boundaries, not every category by default. For global counts/readiness queries, identify fixture producers and their owned cleanup; run producer/consumer tests together where isolation or ordering matters. Locate actual tests rather than copying stale plan class names. Record gaps; add meaningful coverage only where missing. No extra planner, document, or permission gate.

**Mechanism:** For stateful/async/concurrent work, name operation identity, durable target association, surviving facts after restart/expiry/deletion, later lookup/authorization, atomic commits, rollback/pending/replay/late-result behavior. Identify actual fields/queries/boundaries or necessary additions; “handle recovery” is insufficient.

**High-risk checkpoint** applies to authorization, provider/payment effects, destructive changes, migrations, concurrency, recovery:

1. Reviewer traces decisive scenarios. Worker proposes 1–2 early proofs: real entry point, observable state/effects (persisted where relevant), decisive failure/replay/race condition, test. In the existing pre-code exchange, reviewer checks missing facts/lookups/authority/atomic boundaries and whether scenarios expose broken mechanisms. Consolidate feedback; resolve correctness blockers before production edits.
2. Worker implements the smallest complete path for those scenarios, then submits source marker, test location, command/result, and actual assertions through Lead to the same reviewer. Freeze that proof scope during review; **do not expand surrounding implementation yet**.
3. Reviewer inspects executable proof/evidence, not test names/counts. Cross the real application/persistence boundary relevant to risk. Private-validator reflection, method-existence/source-text checks, or mocks bypassing that boundary do not substitute. Reuse fixtures and valid evidence.
4. Lead records acceptance/missing scenario in status. Expand implementation only after reviewer acceptance; then continue autonomously. One bounded checkpoint per risky mechanism, not full candidate review, extra managerial approval, agents/documents, or per-test permission. Reopen only for material mechanism change or invalid evidence, using the same reviewer.

Ordinary low-risk work proceeds after plan publication without acknowledgment or this checkpoint. For new behavior/bugs: meaningful focused RED → implementation → verification; existing tests may supply RED. Compile/setup failures alone are not behavioral proof. Test observable contracts, not invented signatures/structure/wording. Correct faulty tests against requirements with reasons; never weaken valid assertions or alter correct behavior for invented contracts. Preserve repo-required checks.

**Local stalls (including early proof):** After two attempted fixes leave the same underlying failure without meaningful new evidence, stop speculative edits. In the existing plan delta/handoff state expected vs observed behavior, decisive source/log evidence, fixes tried and hypotheses ruled out, remaining uncertainty, and the next discriminating check. Run that focused check, then make an evidence-backed correction; no extra approval for ordinary in-scope repairs. If diagnosis remains uncertain, Lead routes one finite diagnostic to the existing read-only reviewer with the available evidence; reviewer returns diagnosis/hypothesis, next check or smallest repair direction, then ends its turn. No extra supervisor, repeated no-evidence review or new document. This local diagnostic does not itself escalate models; the separate §5 Sol threshold still applies, including proof-level repair candidates. Different causes or concrete diagnostic progress do not trigger this rule; renaming the same failure does not avoid it. Lead watches planning/review loops too and brings unresolved obstacles beyond existing authority to the user. Execution/approval failures use §6's earlier capability diagnostic.

Elapsed time, expected RED, or long tests alone are not stalls. Environment-only failures do not consume attempts, but persistent environment blockers still require diagnosis/supervision. Proof feedback is not one attempt per test; explicit inability/submitted acceptance candidates follow §5. Never keep an exhausted candidate indefinitely “in progress” or “awaiting proof.” Lead's scheduled stall counter is separate (§7).

## 5. Candidate review and escalation

Independent reviewer examines complete affected request/recovery paths for every substantive slice; judge risk by behavior, not diff size. Mechanical corrections stay in existing review. Each blocker: concrete trigger, violated requirement/risk, location, observable impact, closure evidence. No preference/speculative-redesign blockers. Consolidate feedback; flag urgent issues early only to prevent wasted/unsafe work.

**Actionable repair guidance:** With changes-required feedback, reviewer supplies evidence-supported diagnosis (confirmed cause vs hypothesis), smallest credible repair direction, and specific closure assertions. Name relevant functions/fields/boundaries where established. Combine related findings into one short ordered correction plan; mechanical fixes may need only one sentence. Unknown cause → state the uncertainty and next targeted diagnostic, not an invented fix or prolonged investigation. For missing evidence, specify the proof needed rather than assuming production changes. Guidance uses already inspected artifacts; no extra planner, mandatory upfront consultation, full replacement implementation, or per-fix document. Preserve §4's high-risk pre-code/proof checkpoints.

Reviewer remains read-only; accept requirement-correct alternatives, not just compliance with its suggested repair. Lead passes the consolidated guidance to the same worker, resolving scope/dependency conflicts without rewriting the technical plan. Store summary/link with findings; do not duplicate it across tracking files.

**Behavior accounting and ownership:** A milestone is a spec step within the authorized run scope; a slice is a bounded work assignment; a behavior is a stable acceptance target; a candidate is a submitted attempt against that target. Lead keeps one compact record per behavior: `behavior ID + acceptance target | author ID/model + escalation stage | last candidate ID/outcome + Luna/Sol/Astra unsuccessful counts + expert-guided candidate outcome | open finding IDs | accepted source/evidence`. Active records live in status; preserve accepted records with the corresponding progress outcome and link them rather than duplicating live state. Splitting, renaming, compaction or author replacement preserves the records for unresolved targets.

Findings use `finding ID → behavior ID | required outcome | focused evidence + source | open/ready/closed`; they have no separate retry budgets. A candidate with several findings for one behavior consumes at most one unsuccessful attempt for that behavior. Increment the unsuccessful count only when that candidate first becomes unsuccessful, including a demonstrated unmet requirement invalidating an earlier acceptance; repeat reviews do not increment it again. The next corrective submission has a new candidate ID. Existing proof/environment exclusions (§4–§5) still apply. Worker supplies evidence for the closure condition; a passing suite name is insufficient.

Evidence becoming stale solely because of a later authorized source change is not itself a failed candidate. Renew affected evidence before claiming acceptance against the changed source (§6). A discovered defect follows the attribution rules below; submitting a candidate with missing required valid evidence still counts as unsuccessful. Neither evidence renewal nor a milestone transition resets unresolved counts or escalation state.

When a defect appears after acceptance or during integration, use source/evidence to distinguish:

- **Original requirement never actually satisfied:** reopen the original behavior with its prior attempts and escalation state. Route repair to its author when available; a replacement preserves the required model/escalation state and exclusive ownership. Discovery by a newer worker does not transfer or reset the budget.
- **A later change broke previously valid behavior:** attribute the regression to the behavior/change that caused it and use that record's existing budget/ownership, not the affected component's historical failures. Create a new record only for a genuinely new acceptance target; a new symptom of an unresolved defect is not a fresh budget.

If attribution is uncertain, retain existing records and obtain one focused diagnosis using the available source/review evidence before assigning the repair; do not reset counters by assumption. A model escalation applies to the unresolved behavior, not permanently to every future change in those files.

**Reviewer lifecycle (all review stages):**

- Lead dispatches only a concrete ready review: target (mechanism/proof/candidate/correction or §4 bounded diagnostic), source/evidence links, questions, findings to reassess. No "monitor until finished" assignments.
- Reviewer inspects available artifacts, returns a final answer, and ends its turn: `verdict (accepted/changes required/not assessable) | reviewed source/scope | findings + closure conditions | repair guidance when changes required | next needed artifact or none`. Missing evidence → name it and return; never wait for worker changes, future evidence, or broad gates. Missing required evidence on a submitted candidate still follows attempt accounting below.
- Lead stores the returned reviewer ID/path and current findings in status. Retain that reviewer except for §5's explicit expert/implementation handoff. Once required evidence is ready, call `collaboration.followup_task` on that SAME current reviewer with source marker, changed scope, relevant evidence, and unresolved findings. This starts a new turn for a completed/idle agent. Use `collaboration.send_message` for corrections during an active review; it alone does not restart an idle agent. Do not queue speculative reviews, spawn a replacement merely because review completed, or reload unrelated history.
- Return preserves the reviewer for follow-up; it does not delete/close the agent or guarantee a freed capacity slot. If the required follow-up capability is unavailable, report through the existing fallback rule; do not invent a tool or switch to user-owned task messaging.
- Reactivate for ready plan/proof/candidate/correction, §4 bounded diagnostic or invalidated review evidence, not timers/progress chatter. During broad gates Lead checks results; reviewer remains idle unless a defect/source change needs reassessment. No extra review diary or final no-change review round.


- Initial/corrective candidate: focused + neighboring checks, including affected shared-contract/fixture checks from §4, **before the next broad cycle**. After corrections, renew the affected map/checks and reuse valid evidence; update outdated test expectations only against the governing contract, preserving required historical compatibility. Lead checks evidence completeness; reviewer decides substantive closure. Review clearance remains provisional until broad gates pass. Preserve explicitly required earlier repo checks; no broad reruns merely to request review.
- Submission includes scope, tested source marker, commands/results, concerns. Freeze reviewed scope until consolidated feedback or explicit withdrawal. Use §6's lightweight tested-source identification; no mandatory whole-repo or evidence-file hashing. Disclose later changes; renew affected evidence.
- Return blockers as one cohesive correction. Re-review changes/unresolved findings; expand only for concrete risks introduced by fixes. If broad gates reveal a defect, correct it and renew affected review/verification. Lead checks evidence completeness without duplicating independent technical review.

**Luna: initial candidate + four correction rounds → Sol Medium:** Allow up to five candidate attempts for the same unresolved behavior: initial candidate = attempt 1; corrections 1–4 = attempts 2–5. Stop correcting as soon as the candidate is accepted. An attempt is a submitted acceptance candidate or explicit inability to meet agreed behavior. Validated unresolved requirements, including missing behavioral evidence at Lead's completeness check, make submission unsuccessful even before broad gates. Local iterations, expected RED, plan feedback, and environment-only failures do not each count.
