# Execution and recovery

Read before command/browser ownership, a real capability failure, stalled execution or an expensive performance retry. Follow actual tools, repository instructions and permissions; this reference grants no additional access.

## Ownership and autonomous execution

In the batch brief name the command families/directories, focused/neighbor checks, access route, log location, shared resources, cleanup obligations and next candidate/checkpoint. Record the agreement once. Worker owns its commands through results or an explicit safe transfer, including resumable handles, fixture restoration and server teardown. Lead does not duplicate polling or request a handoff after every command.

Routine commands with observable tool responses need no separate launch notice. If the first approval-sensitive operation may wait without a shared response/handle, include its concrete launch window and expected response in the existing plan so the Lead can diagnose a missing response. Retain actual command/directory/start, approval outcome or unknown, initial response/handle and final result; existing tool timestamps and retained output suffice when they establish those facts. Later covered selector repairs, runs and handle resumes need no new managerial permission or per-command notices. Renew the agreement only for material changes in scope, access, shared-resource risk or restoration. Actual tool approvals always apply; never infer authorization from silence or vary commands to bypass rejection.

One writer/owner controls a shared file, output directory, port/server, database fixture or persistent browser profile at a time. Queue conflicting operations; independently ready work continues. Read-only review and gates may overlap only on the same frozen inputs with compatible resources. If a full gate consumes the whole checkout, all source/config/fixture writers must reach a stable boundary before it starts. Other edits require real source isolation, not merely separate assignments. Preserve unrelated processes, containers, profiles and user tabs.

## Browser preflight and reuse

Prefer the built-in Browser/Computer Use when applicable. Discover through callable entry points and actual inventory, read exposed API documentation, and check availability for the intended executing agent/session. A missing named skill is not proof of absence, and Lead availability is not proof of worker availability. Record one named browser owner and the observed working route.

If a permitted built-in Browser is available only in the main chat, the Lead can own interactive verification while workers own source/fixtures/servers; this is a normal allocation within existing authority, not a request for extra access. A genuine denied approval or forbidden operation cannot be bypassed by moving it to the Lead. Unsupported roles/tools still follow the core capability rule.

Establish a working HTML/app check: fresh rendered document, observed interaction/result, console inspection and screenshot. Do not navigate to a standalone SVG as a health check when automatic snapshots expect HTML. Inspect supported fixture APIs before reuse. Verify required API base/auth/env settings, new-document behavior and uniquely tagged fixture requests before accepting results. A same-document hash change or a skeleton with no tagged requests does not establish fixture ownership; reload when needed. Reuse a valid harness across consumers and read installed invocation semantics before adapting it.

Use a supported fallback only after confirmed absence or a diagnosed invocation failure, under the recovery limits. Reassess after relevant runtime changes. Required automated E2E remains required. Browser evidence has the boundaries it actually exercises: synthetic HTTP is not database/provider persistence, and a DOM assertion is not assistive-technology speech.

Keep interactive scenarios finite and use supported tool timeouts. If a native file picker or other UI operation stops returning useful evidence, diagnose its execution state promptly; do not leave a dependent workstream waiting for hours. Use a supported equivalent fixture/upload API when it meets the same acceptance target and is authorized, documenting any remaining native-interaction gap. Do not fabricate a native check or kill a live operation blindly.

Close owned temporary tabs/contexts through supported APIs before handing over, preserving unrelated tabs. Follow repository/version-specific release checks. For Playwright MCP versions where tab listing can launch a browser, `browser_close` is the final browser call; verify release by read-only exact-profile/process ownership inspection, not another tab listing or a lock-file guess. Never blindly kill Chrome or delete profile locks. If release is uncertain, stop dependent browser work and retain the cleanup obligation. Do not assume per-call VM globals or navigated page globals survive; drain owned handlers and restore fixtures as the installed APIs require.

## Concise evidence

Retain verbose output in a log and return `command + directory | result/exit status | tested source | log/proof link | limitation`. Preserve the actual process/pipeline result; a shell wrapper's zero does not prove a nested test passed. For failure, include the decisive excerpt and affected operation. Inspect more output only for a concrete diagnostic or evidence gap, not repeated successful-test listings.

Use one existing evidence index with a named writer. Retain essential command/source/result summaries durably; do not leave the only acceptance evidence in disposable logs. Identify uncommitted/untracked reviewed source with an adequate scoped diff, manifest or snapshot; a commit alone covers only committed files. Do not mandate archives/hashes for every log or recursively checksum packages. Original completion plus retained output is valid evidence; a missing duplicate `.exit` file is not a reason to repeat a known successful gate. Investigate genuinely uncertain completion/source applicability before claiming a pass.

## Resource-aware progress assessments

At the core's existing assessments and milestone acceptance, compare accepted requirements with remaining dependencies, repair cycles, elapsed time and readily available usage. Use exposed telemetry or existing summaries; avoid new polling, session-history mining or another monitoring process. Label missing values and distinguish run-specific tokens, shared account allowance and monetary charges; none alone establishes the others.

Honor any user-defined time/usage budget as a stopping boundary. Reserve capacity for required verification, cleanup and handover; at a safe boundary checkpoint before starting a batch unlikely to fit. With no explicit budget, limited allowance calls for smaller coherent batches and a recoverable checkpoint, not an invented quota or early stopping rule. An allowance warning never authorizes weaker checks, scope reduction, paid usage or silent model substitution. Respect actual hard limits and report incomplete scope honestly.

When comparing workflow variants, keep acceptance requirements and evaluation conditions comparable. Include completed requirements, defects/repair cycles, elapsed time, usage and human intervention; compare efficiency only for outcomes meeting the quality bar. Source review and small decision exercises cannot establish production speed or cost gains.

## Native waits

Use direct native event-aware waits. Lead requests up to **600 seconds**; a subagent awaiting a necessary coordination decision up to **120 seconds**. Bound each by exposed tool limits, higher-priority instructions and the next actual progress/diagnostic deadline. Urgent messages, completions and user input are handled promptly. Do not wrap agent waits in `functions.exec`/`functions.wait`, sleeps, monitor agents or automations. Command-handle waits follow their own tool limits and stay with their owner.

After a timeout with no new information and no due deadline, wait again. Do not read logs/status, inspect agents, rewrite tracking or request progress merely because a timeout occurred. A known pending decision is resolved/routed before Lead waits. If an unanswered blocking request has not been routed after the worker's first interval, one clarification is allowed; no repeated reminders for an already active review. Reviewers with no assessable artifact return and end their turn.

Native waits do not guarantee reactivation after the main turn ends. Preserve actual deadlines across early returns/compaction; never infer elapsed time from a requested wait. If the effective runtime enforces shorter intervals or commentary, obey it and disclose that limit once; do not change configuration or claim savings the runtime cannot provide. Routine no-change user updates use known state and do not justify extra polling.

## Missing-response and capability diagnostic

After **five minutes without initial response or execution evidence** from a concretely launched operation, inspect its named evidence and available state once at the next supported boundary. A planned operation not launched is not stuck. An active returned handle is monitored normally, not classified as missing. Actual approval rejection is an execution blocker; report it accurately and do not cycle command variants.

Once the route works, do not create a new Lead timer or notice for every covered run. At a relevant event/progress assessment, act immediately on concrete evidence that a later invocation has lacked its initial response for five minutes. Without native notifications, exact five-minute detection of every later invocation is not guaranteed; do not emulate it with periodic file polling. Legitimate long but progressing tests are not interrupted merely for elapsed duration.

If state is unclear, obtain one finite owner diagnostic: operation/directory, last response, approval known/unknown, handle/process state, pending mutations/restoration and next discriminating action. Safely interrupt/reactivate a worker turn if necessary and supported; interruption does not prove the underlying process stopped. Preserve command ownership until it is settled or explicitly transferred.

Permit **one evidence-based authorized recovery** for the identified capability cause. Establish whether prior execution is still active and settle temporary mutations before retrying. Do not broaden permissions, change arbitrary profiles/endpoints/limits, reset recovery counts through a new agent or substitute models for denied access. Recurrence of the same capability blocker, another missing initial response after recovery, or no justified recovery requires a checkpoint and human capability/fallback decision for dependent work. Keep the recovery history across handoffs; do not wait for two scheduled assessments. Continue independently ready authorized work. A supported same-authority ownership assignment is allowed; a denied/unknown access outcome is never bypassed.

Checkpoint the exact operation, actual elapsed time, known/unknown state, recovery and cleanup obligations. For a whole-run pause use the core pause/resume rules. A fallback requires only a genuinely unresolved decision, not renewed permission for ordinary in-scope commands, supported ownership or an already authorized repair.

## Expensive resource/performance failures

After the first representative failure at a required time, memory or volume limit, stop speculative full-size reruns. Use existing logs/tracing and the smallest faithful diagnostic at the relevant shape and fixed runtime caps. Measure the suspected phase: end-to-end time including commits/locks, retained versus temporary memory/GC, or query/batch counts. A timeout stack locates where failure surfaced, not necessarily its cause. Mark downstream phases and sampling limits not yet exercised.

Before another expensive acceptance run, author and independent reviewer establish the measured cause or discriminating hypothesis, targeted correctness-preserving repair, representative capped improvement and feasibility of the complete remaining path. A faster helper/small case or extrapolation near a limit alone is insufficient. Reuse observations in the existing evidence index; no new profiling infrastructure, assessor, margin gate or full-size proof twice merely for reassurance.

A success with valid evidence closes the gate; disclose tight margins without automatic optimization/reruns. Never silently raise limits or weaken assertions. If feasibility remains uncertain, return the next bounded diagnostic or material human decision. Submitted failed repairs still count under the review reference, even when one phase improves and another fails; environment-only failures do not consume implementation attempts.
